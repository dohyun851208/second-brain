# 갱신절차

## 1. 컴파일 (새 원본 반영)

새 원본이 `0_원본/`에 추가되면 `파서-프롬프트.md`(파싱 → `1_파싱/`) → `컴파일러-프롬프트.md`(증류) 순으로 실행한다.
항상 **증분**으로 — index.md 대장에 파싱·반영 안 된 파일만.

`5_규범자료/`·`6_참고자료/`에 새 자료가 들어오면 **파싱까지만** 하고 증류는 하지 않는다 (파싱본은 원본 옆에 저장).
증류 단계로 넘기지 않으므로 대장에도 등록하지 않고, 해당 폴더 `자료목록.md`의 행을 갱신한다.

## 2. 피드백 반영 (판단이 어긋났을 때)

사용자가 "그 판단은 나답지 않다"고 하면:
1. 어떤 규칙이 그 판단을 만들었는지 역추적한다 (응답에 규칙 번호가 있으므로 가능)
2. 규칙을 수정하거나 확신도를 낮춘다
3. log.md에 기록: 무엇이 왜 바뀌었는지

## 3. lint 패스 (증류 꼬리 — 증류가 끝나면 이어서 실행, "점검해줘"로 단독 호출도 가능)

달력·횟수 주기는 두지 않는다. 증류는 사용자의 수동 수집에 묶여 자주 일어날 수 없으므로, 증류 꼬리에 붙이는 것만으로 "가끔"이 자연스럽게 보장된다. 새 재료로 두뇌 모양이 막 바뀐 직후라 "무엇이 얇은가"도 가장 정확하다. 증류를 한동안 안 해 점검이 궁금하면 "점검해줘"로 언제든 단독 호출한다.

### 위생 점검 (지금 있는 게 멀쩡한가)

- [ ] **모순 규칙**: 서로 충돌하는 규칙이 있는가 → 있으면 사용자에게 확인 (성향 변화 vs 예외)
- [ ] **낡은 규칙**: 최근 대화·피드백과 어긋나는 오래된 규칙이 있는가
- [ ] **출처 잃은 인용**: 출처 링크가 가리키는 파싱본·원본 파일이 아직 존재하는가
- [ ] **파싱 신선도**: 대장의 파싱본이 실제 `1_파싱/`에 있고, 기록된 수정시각이 원본과 일치하는가 (낡은 파싱본 → 재파싱 제안)
- [ ] **인용 없는 규칙**: 원문 근거 없이 확신도 "중간" 이상인 규칙이 있는가 (있으면 강등)
- [ ] **팩트카드 신선도**: "최종 갱신"이 1년 넘은 섹션이 있으면 사용자에게 갱신 제안
- [ ] **index 정합성**: index.md의 모듈 목록·규칙 수·원본 반영 대장이 실제 `2_두뇌/` 파일 및 `0_원본/`·`1_파싱/`과 일치하는가 (미등록 고아 모듈, 파일 없는 유령 등록 없음)
- [ ] **개인정보 이미지 격리**: `7_개인정보이미지/`가 파싱·대장·두뇌에서 제외되어 있는가. `0_원본/`에 서명·도장·신분증·통장사본·증명사진처럼 원형 재사용 자산으로 보이는 이미지가 있으면 이동을 제안한다
- [ ] **자산 목록 정합성**: `7_개인정보이미지/자산목록.md`의 경로와 실제 파일이 일치하며, 사용 기록에 주민번호·계좌번호 등 민감 값이 적히지 않았는가
- [ ] **5·6층 격리**: `5_규범자료/`·`6_참고자료/` 출신 파싱본이 `1_파싱/`이나 index 대장에 섞이지 않았는가. `2_두뇌/`에 남의 자료를 요약한 모듈이 생기지 않았는가 (생겼으면 해당 폴더로 이동 제안)
- [ ] **규범 범위 공백**: `5_규범자료/자료목록.md`에 **범위** 칸이 빈 행이 있는가 → 있으면 채우도록 요청한다. 범위를 모르면 "없다"고 답할 수 없어 인용 문이 작동하지 않는다
- [ ] **지난판 정리**: 상태가 `현행`인 규범자료 중 같은 자료의 신판이 들어와 있는데 이전 판이 아직 `현행`인 것이 있는가 (있으면 `_지난판/` 이동과 상태 갱신 제안)

### 성장 제안 (무엇을 넣으면 두뇌가 자라나)

위가 "지금 있는 게 멀쩡한가"라면, 이건 "무엇을 넣으면 자라나"다. **자동 투입은 없고 제안만 한다** — 넣을지는 사용자가 정하고, 안 넣어도 비용은 0(그 영역이 얇은 채로 남을 뿐이며, 그건 사용자가 그 작업을 덜 한다는 정직한 반영이다). 억지로 채운 두꺼운 두뇌보다 얇아도 정직한 두뇌가 판단 엔진엔 낫다.

- [ ] **얇은 모듈**: 규칙 수가 유독 적은 모듈 → 그 영역의 대화·문서를 `0_원본/`에 넣어보라고 제안
- [ ] **갇힌 확신도**: 근거 대화가 1개뿐이라 확신도 "낮음"에 묶인 규칙 → 비슷한 상황의 대화를 더 넣으면 확신도가 오를 후보라고 안내
- [ ] **커버리지 공백**: 사용자가 자주 하는 작업인데 관련 규칙이 없는 영역 → 해당 작업 대화 제안
- [ ] **보류 가설**: `8_시스템/가설-기록.md`의 "보류(맥락 의존)" 항목 중 새 자료로 판별 가능해 보이는 것 → 어떤 자료가 있으면 결론 낼 수 있는지 제안
- [ ] **규범 공백**: 사용자가 자주 만드는 문서에 필요한 규범 범위가 `5_규범자료/`에 없어 인용을 못 하고 물었던 적이 있는가 → 해당 문서를 넣어두라고 제안 (넣으면 다음부터 묻지 않는다)
- [ ] **참고자료 채택 흔적**: `6_참고자료/`를 재료로 쓴 작업이 있었는데 무엇을 채택·폐기했는지가 `0_원본/`에 남지 않았는가 → 그 판단은 사용자의 것이므로 저장하면 규칙이 된다고 제안

## 4. kordoc 호환성 점검

"세컨드브레인 상태/업그레이드" 요청 때 실행한다. 일반 세션마다 네트워크 조회하지 않는다.

1. 실제 실행판: `npx -y kordoc@^4 --version`
2. npm 전체 최신판: `npm view kordoc version`
3. 최신판이 4.x면 실행 시 이미 자동 적용된다. 버전만 보고 시스템 파일을 교체하지 않는다.
4. 새 기능·동작 변경이 파싱·산출 절차에 영향을 주면 공식 변경 기록을 확인하고 `파서-프롬프트.md`·`9_형식/references/kordoc.md`·`9_형식/라우팅.md`를 함께 고친다.
5. 최신판이 5.x 이상이면 자동 전환하지 않는다. 대표 HWP/HWPX·스캔 PDF·이미지·XLS 문서로 파싱/patch/fill/validate 스모크 테스트 후 `@^4` 범위와 시스템 지침을 함께 올린다.
6. 파싱본 frontmatter의 `도구-버전`으로 과거 결과의 엔진 버전을 추적한다.

## 5. 버전 규칙

- 규칙 추가·수정: 소수점 증가 (v1.0 → v1.1)
- 첫 컴파일 완료, 또는 구조 변경(모듈 추가 등): 정수 증가 (v0.x → v1.0)
- 버전은 index.md 상단과 log.md에 기록
- **시스템 버전**(`AGENTS.md` 주석)은 별도: 스킬 `templates/`의 시스템 파일을 수정하면 반드시 함께 올린다 (업그레이드 감지는 이 숫자 비교로만 작동)
